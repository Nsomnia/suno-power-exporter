Library sync

A sync crawls your Suno feed and writes every clip it finds into a local index. Nothing is downloaded; this only builds the list you filter over.

Sync behaviour

Hard cap on feed pages walked in one run (1–2000). Reaching the cap makes the crawl truncated: the library on disk is then INCOMPLETE and every surface says so. Raise it if clips are missing; lower it if a sync takes too long.

Suno has no per-clip dislike field. A dislike is only known by diffing the feed fetched with dislikes hidden against the feed fetched with them shown. So the honest filter costs two crawls: both pages the feed twice and roughly doubles sync time, and that is the only mode that gives you a true include/exclude-downvoted filter. exclude guesses that anything not in the shown feed is a dislike (fast, wrong for clips deleted or hidden for other reasons). include treats every crawled clip as a keeper (fast, keeps dislikes).

Off by default. When on, the worker keeps a periodic alarm and re-runs a resumable crawl without deleting anything already indexed. The first auto-sync after a long gap still walks every page.

5–1440. Only used when auto-sync is on. Chrome enforces a minimum alarm period, so a very short interval is rounded up in practice.

Download

Suno meters downloads, not credits: free 0 / pro 20 / premier 60 per billing period, resetting on the billing date, with no carryover. One song costs one download whatever the format you ask for.

Format

Passed straight through as the download route's ?format= parameter. The legal values of that enum are undocumented, so which of these actually return audio is something the extension learns from use rather than knows up front — a rung that fails simply falls through to the next one in the ladder.

Source ladder order matters — the first rung that can deliver the clip wins

Cost classes. UNMETERED progressive and mango-drm read Suno's own media URLs and never touch the download meter. METERED studio, download-route, wav-official and zip each consume one of your monthly downloads. Keeping every metered rung below the unmetered ones is the only thing that guarantees a batch spends zero downloads, because when a rung fails for a clip the driver falls through to the next one in this order.

Not a bypass. An old exploit in which the Studio route served files without counting them was closed server-side on 2026-09-09. The METERED labels above are the observed contract, not a workaround.

Enabled rungs, in order

    The ladder is empty. No batch can run until at least one rung is added — the worker refuses to start rather than guessing.

    Available rungs

      Mid-batch quota guard

      The allowance is read once before a batch is planned and then again during it. Without the re-check, a plan built on a stale reading used to run on until every remaining clip failed one by one on the metered rungs — a healthy badge and an opaque failure. These two numbers are the guard that stops the batch cleanly instead.

      0–10000. The floor the guard stops at: once a re-read reports remaining ≤ this, the batch halts cleanly with a warning instead of failing clip by clip. 0 means stop exactly at zero — the batch ends the moment the meter empties, having spent nothing it did not have to. Leaving headroom costs you that many downloads per period but buys a hard guarantee that a batch can never overrun the allowance between two re-reads.

      1–100. How often the meter is re-read, counted in successful metered downloads. Unmetered rungs never consume the allowance, so they never trigger a check: a batch served entirely by progressive / mango-drm spends zero extra requests. A higher N is cheaper but notices exhaustion later, so a batch can overshoot your reserve by up to N−1 downloads before the guard fires. The default of 5 is the compromise; the pre-batch preflight reads the meter regardless of this value.

      A re-read that cannot be answered is treated as unknown, never as zero: a failed quota fetch leaves the batch running rather than stopping it on a guess. A dry run polls nothing and can never be stopped by this guard.

      Cost and safety

      Off by default. Required before the wav-official and zip rungs can be added at all — both are metered, and both are opt-in rather than merely ordered. With this off, the worker silently drops them from the ladder rather than spending your downloads.

      Off by default: a clip already recorded as downloaded for this format is skipped, which is how a re-run avoids burning quota on files you already have. Turn this on only when you deliberately want replacements; every re-download spends quota again.

      64 KiB–64 MiB. Below this a file is saved through a data: URL; above it the worker asks the offscreen page to mint a blob URL, which is far cheaper for large WAVs. The default (24 MiB) is a good balance; lowering it wastes memory on big files.

      Pacing and retries

      1–8. Higher is faster and more likely to be rate-limited.

      0.2–20, shared by every network call the extension makes.

      0–5, per clip, after the first try. Retries are for transient failures only: a 403 entitlement wall and an explicit refusal are never retried.

      On by default. Spreads the configured rate randomly instead of firing at a perfectly regular interval, which is the difference between looking like a browser tab and looking like a script.

      Naming and folders

      Filename template

      A clip title is attacker-influenced text that ends up on your filesystem, so the result is sanitised: control characters and bidi overrides are stripped, \ / : * ? " < > | become _, runs of dots collapse so .. can never survive, leading and trailing dots and spaces are trimmed, Windows device names are prefixed, and the basename is capped at 180 characters.

      Use / to create folders. A leading / is rejected — the path is always relative to your downloads folder. A .. segment cannot escape it.

      The extension is appended automatically if you leave {ext} out, so {title}_{clipIdShort} still produces Title_a1b2c3d4.m4a. Keeping {ext} in the template makes the intent obvious; an unknown token becomes _ rather than literal braces.

        Tags and sidecars

        MP3 gets an ID3v2.3 tag (TIT2 title, TPE1 artist, TALB album, TCON genre, TDRC year, TBPM tempo, COMM provenance comment, USLT lyrics, APIC artwork). M4A gets iTunes atoms (©nam, ©ART, ©alb, ©gen, ©lyr, covr) written by hand, because there is no MP4 tag library here. WAV gets a RIFF LIST/INFO chunk and a RIFF chunk literally named id3 , so the same metadata is readable by DAWs that understand either.

        Artwork roughly doubles the file size. A 4 MB track becomes an 8 MB file. Turn Embed artwork off and fetch covers yourself if size matters more than having the image travel with the audio.

        Embedded tags

        Master switch. Off means every file is written untagged, whatever the individual options below say.

        USLT on MP3, ©lyr on M4A. Raw LRC timestamps are stripped, because unsynchronised lyrics carrying timestamps is just noise.

        APIC / covr. The full-size image is fetched per clip, and the file roughly doubles in size. A cover that cannot be fetched degrades to "no artwork", never to a failed download.

        TBPM / tmpo. Off by default because it costs: when a clip carries no tempo the worker measures one from the decoded audio, which adds real time per file. A missing BPM is never invented.

        COMM / desc. Records the model version, the clip id and the prompt and style text, so a file can be traced back to what produced it.

        Sidecar files written next to the audio

        Timed lyrics. Only written when the clip actually has lyrics.

        A machine-readable record of the clip. It contains no session token or key material, but it does contain the prompt text.

        A plain .txt lyric file is always written alongside when the clip has lyrics; it is not optional. A sidecar is never counted as a song and never spends a download.

        Audio conversion

        Transcode

        Every conversion here runs on this machine. Any choice but Nothing is a real local render: the delivered bytes are decoded to PCM and written back out in the format you pick, so it costs wall-clock time and peak memory of roughly one decode plus one encode per track. It spends no download quota — transcoding happens after the fetch, so the meter only ever sees the rung that delivered the clip, and with the unmetered progressive / mango-drm rungs serving it, a transcode costs none of your monthly allowance. What it buys is a file in a container you picked on purpose: M4A and Opus already are one, WAV is the safe interchange format, and MP3 and Ogg Vorbis are there for players that take nothing else. Both encoders are vendored under vendor/ rather than pulled from a CDN, because MV3’s script-src 'self' CSP forbids remote script outright.

        Convert the downloaded audio to

        Nothing: the file is written exactly as the ladder delivered it, and nothing is decoded at all. M4A and Opus never need a transcode, because the source stream already is one — so for the default variant this is both the cheapest and the most faithful choice.

        WAV: the bytes are decoded, resampled to the rate below and written with a real RIFF header by the offscreen page. No codec loss and nothing is thrown away, but the file gets large: an uncompressed 48 kHz stereo track runs to roughly 11 MB per minute.

        MP3: a real encoder runs locally in the offscreen page, vendored as vendor/lame.all.js (lamejs 1.2.1, LGPL-3.0). Nothing is uploaded and no server is contacted — your audio never leaves the machine. The track is decoded to PCM and re-encoded, so the result is lossy and smaller than the source; it cannot put back anything the decode discarded, which is why the bitrate below is the only size knob here.

        Ogg Vorbis: encoded locally by vendor/OggVorbisEncoder.js, on your own machine, with no upload and no external service — the same privacy property as MP3, and the same cost: one decode plus one re-encode per track, lossy. Vorbis generally reaches a given perceived quality at a smaller file than MP3 does, but far fewer players and DAWs accept it, so it is not the safer default. Pick it because something downstream needs Vorbis.

        Used only when the transcode above is set to WAV; it stays disabled for every other choice. The output rate is whatever this field requests — that is the rate written into the RIFF header, because the offscreen renderer actually resamples to it. MP3 and Ogg Vorbis get no rate of their own: they are encoded at the offscreen page’s decode rate of 48 kHz, so a 44.1 kHz source is resampled on the way in and there is no control over it here.

        No hidden upsampling. A previous version of this page advertised a “WAV 48 kHz” format option while nothing resampled at all. Nothing here invents detail either: asking for 48 kHz from a 44.1 kHz source produces a 48 kHz file by interpolation, not 48 kHz of audio. Requesting 96 or 192 kHz enlarges the file and the header without adding information.

        Written as mp3Bitrate and read only while the transcode above is MP3; it stays disabled for every other choice, and the value you pick is kept while it is disabled, so switching MP3 → Ogg Vorbis → MP3 does not lose it. These six are the six bitrates LAME accepts at full quality — ask it for anything else and it substitutes its own without telling you. A three-minute track comes to roughly 2.9 MB at 128, 4.3 MB at 192 and 7.2 MB at 320, before tags and artwork. Higher is not better forever: the source was already decoded once, so a higher bitrate only preserves more of whatever survived that decode.

        Written as oggQuality and read only while the transcode above is Ogg Vorbis; it stays disabled for every other choice, and is likewise kept across format switches. This is the encoder’s named-quality index on a 0–1 scale rather than a bitrate: 0.0 is the smallest and fastest encode, 1.0 the largest and slowest, and 0.0–1.0 is not a size measurement. The worker snaps anything between two tenths to the nearest tenth, so every entry here is exactly what the encoder is handed — which is why this is a list you pick from and not a number you can type.

        Advanced

        Capture and planning

        Off by default, and enabling it is a deliberate act. This option lets the page collect a clip’s stream segments, and the only way to do that on Suno’s own player is to temporarily set window.MediaSource = undefined so the player falls back to a plain fetch. That manipulates the page, can disturb playback, and can trip abuse heuristics on Suno’s side. The content script asks for an explicit confirmation too, so both this page and the page itself must agree. It is also not part of the download ladder: with it on, stream capture is simply an extra path the worker will accept.

        The batch is planned, quota-preflighted and recorded, and then stops. No bytes are fetched and no download quota is spent. This is the safe way to find out what a filter will match.

        Turns on the extension’s ring-buffered diagnostics. Useful when reporting a problem; it records clip ids and request codes locally, so leave it off unless you are debugging.

        Backup and reset

        An export contains your settings, the cached workspace list and the last known download balance. It deliberately contains no session token and no key material, and not the diagnostics log — which would carry clip ids you would not expect to leave the machine.

        Reset changes settings only. Your indexed library, download history and any files already saved to disk are untouched.
